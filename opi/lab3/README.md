## Проверка целей по отдельности

Каждая цель запускается самостоятельно и не требует остальных, кроме объявленных зависимостей:

```bash
./gradlew clean              # очистка
./gradlew compile            # компиляция
./gradlew build              # compile + JAR
./gradlew test               # build + JUnit
./gradlew xml                # валидация XML
./gradlew func-tests         # функциональные тесты в Docker
./gradlew func-tests-local   # функциональные тесты без Docker
./gradlew history            # поиск последней рабочей ревизии
./gradlew tasks --group lab4 # список всех целей лабораторной
```

Если порт 8080 или 3000 занят другой программой, Docker откажется запускать контейнер с ошибкой `address already in use`. Найти и освободить порт:

```bash
lsof -nP -iTCP:8080 -sTCP:LISTEN   # показать процесс, занявший порт
kill <PID>                         # завершить его
```

Удаляет результаты сборки и тестовые отчёты:

```bash
./gradlew clean
```

Сначала выполняет `build`, затем запускает 9 модульных JUnit-тестов:

```bash
./gradlew test
```

Принудительный повторный запуск тестов:

```bash
./gradlew test --rerun-tasks
```

Отчёт:

```text
backend/build/reports/tests/test/index.html
```

Собирает проект, затем поднимает PostgreSQL, backend, frontend и Playwright в Docker и прогоняет функциональные тесты в контейнеризированном окружении:

```bash
./gradlew func-tests
```

Цель выполняет:

```bash
docker compose -f docker-compose.test.yml up --build --abort-on-container-exit \
    --exit-code-from functional-tests functional-tests
```

Код завершения контейнера с Playwright становится результатом задачи; контейнеры останавливаются автоматически. Node.js на хосте не требуется.

### func-tests-local

Тот же набор функциональных тестов, но **без Docker**: Playwright запускается прямо на машине. Приложение должно быть уже запущено и доступно по адресу `http://localhost:3000`.

```bash
./gradlew func-tests-local
```

Цель сама ставит зависимости (`npm install`) и браузер Chromium (`npx playwright install chromium`), затем запускает тесты.

Чтобы поднять приложение без Docker, нужны запущенный PostgreSQL на порту 5431, backend и frontend:

```bash

cd frontend && npm install && npm start          # во втором терминале
```

Проверяет корректность (well-formedness) XML-файлов проекта, включая `backend/src/main/resources/logback-spring.xml`. Служебные каталоги `build`, `node_modules`, `.gradle`, `.idea` исключены:

```bash

```

Ожидаемый вывод:

### history

Если текущая ревизия не компилируется, ищет последнюю рабочую ревизию и сохраняет изменения первой сломанной ревизии:


Результат:

Перед запуском рабочее дерево Git должно быть чистым:

Docker-вариант проверяет все ревизии в одинаковом Java-образе:

## Функциональное тестирование: теория

### Что это такое

**Функциональное тестирование** отвечает на вопрос «делает ли программа то, что должна». Проверяется поведение системы с точки зрения пользователя: ввели данные — получили ожидаемый результат. Внутреннее устройство при этом не важно, поэтому такой подход называют **тестированием чёрного ящика** (black box): мы не смотрим в код, мы смотрим на поведение.

Противоположность — **нефункциональное тестирование**: оно отвечает на вопрос «насколько хорошо программа это делает». Сюда относятся нагрузочное (выдержит ли 1000 пользователей), тестирование безопасности, удобства использования, совместимости с браузерами. В этой работе нефункциональное тестирование не выполняется.

Ещё есть **тестирование белого ящика** (white box) — когда тесты пишутся с знанием внутренней структуры кода. Наши модульные JUnit-тесты как раз такие: они вызывают конкретные методы конкретных классов.

### Уровни тестирования

Тестирование принято делить на четыре уровня — от самого мелкого к самому крупному:

| Уровень | Что проверяет | Пример в этом проекте |
|---|---|---|
| Модульное (unit) | Отдельный класс или метод в изоляции | `PointsServiceTest` проверяет метод вычисления попадания точки |
| Интеграционное | Взаимодействие нескольких модулей | Backend + база данных: сохранилась ли точка |
| Системное | Систему целиком, через интерфейс пользователя | Наши Playwright-тесты: браузер → frontend → backend → БД |
| Приёмочное (acceptance) | Соответствие требованиям заказчика | Проверка, что реализованы все пункты задания |

Наши функциональные тесты — **системного уровня**: они запускают настоящий браузер и работают со всей цепочкой сразу.

### Пирамида тестирования

Классическая рекомендация о том, сколько каких тестов писать:

```
        /\        мало     E2E / системные тесты  — медленные, хрупкие, но реалистичные
       /  \
      /----\      средне   интеграционные тесты
     /      \
    /--------\    много    модульные тесты        — быстрые, стабильные, дешёвые
```

Логика простая: модульные тесты выполняются за миллисекунды и точно указывают на сломанный метод, поэтому их должно быть много. Системные тесты запускают браузер, базу и сеть — они медленные и могут падать из-за случайностей, поэтому их берут немного, но на самые важные сценарии.

В нашем проекте 9 модульных тестов и 15 функциональных. Это не совсем «пирамида» — но для учебной работы задание прямо требует 15 тест-кейсов, и они покрывают ключевые пользовательские сценарии.

### Жизненный цикл тестирования (STLC)

**STLC** — Software Testing Life Cycle, последовательность этапов работы тестировщика. Шесть фаз:

**1. Анализ требований.** Изучаем, что вообще должно работать. Ищем неоднозначности: например, «Y должен быть в диапазоне (-3; 5)» — границы включаются или нет? Круглые скобки означают, что не включаются, но это стоит уточнить, потому что от ответа зависят тест-кейсы. Результат фазы — понимание, что тестировать.

**2. Планирование тестирования.** Решаем: что именно проверяем, чем, кто это делает, сколько времени займёт, какие риски. Определяем **критерии входа** (когда можно начинать: например, приложение собирается и разворачивается) и **критерии выхода** (когда можно считать тестирование законченным: например, все кейсы выполнены и критических дефектов нет). Результат — тест-план.

**3. Разработка тест-кейсов.** Пишем сами кейсы: шаги, данные, ожидаемый результат. Применяем техники тест-дизайна (см. ниже), чтобы не проверять всё подряд, а покрыть главное минимальным числом проверок. Результат — набор тест-кейсов и тестовые данные.

**4. Настройка тестового окружения.** Готовим среду, где тесты будут выполняться: развёрнутое приложение, база с нужным состоянием, браузер, тестовые учётные записи. Именно эту фазу у нас закрывает Docker: `docker-compose.test.yml` поднимает базу, backend, frontend и контейнер с браузером — окружение создаётся одной командой и одинаково на любой машине.

**5. Выполнение тестов.** Прогоняем кейсы, фиксируем фактический результат. Если фактический не совпал с ожидаемым — заводим **дефект** (баг-репорт). После исправления выполняем **повторное тестирование** (retest) — проверяем, что конкретный дефект исчез, и **регрессионное тестирование** — проверяем, что исправление не сломало то, что работало раньше.

**6. Завершение тестирования.** Подводим итоги: сколько кейсов выполнено, сколько прошло, какие дефекты остались открытыми. Результат — отчёт о тестировании. У нас его роль выполняют колонка «фактический результат» в кейсах и HTML-отчёт Playwright.

### Жизненный цикл дефекта

Отдельный цикл — путь найденной ошибки:

```
Новый (New) → Назначен (Assigned) → Исправлен (Fixed) → Проверен (Verified) → Закрыт (Closed)
                     │                                          │
                     ├→ Отклонён (Rejected)                     └→ Переоткрыт (Reopened),
                     ├→ Дубликат (Duplicate)                        если дефект остался
                     └→ Отложен (Deferred)
```

**Баг-репорт** должен содержать: заголовок, шаги воспроизведения, фактический результат, ожидаемый результат, окружение (браузер, версия), приоритет и серьёзность. **Серьёзность** (severity) — насколько сильно ломается функциональность; **приоритет** (priority) — насколько срочно чинить. Это разные вещи: опечатка в названии компании на главной странице имеет низкую серьёзность, но может иметь высокий приоритет.

### Тест-кейс и его атрибуты

**Тест-кейс** — это описание одной проверки: при таких-то условиях выполняем такие-то шаги и ожидаем такой-то результат.

Обязательные атрибуты (именно они в таблицах ниже):

| Атрибут | Зачем нужен |
|---|---|
| id | уникальный номер для ссылок и отчётов |
| тип | позитивный или негативный |
| проверяемая функция | какая функциональность проверяется — помогает видеть покрытие |
| название | короткая суть кейса |
| предусловие | в каком состоянии должна быть система до начала |
| тестовые данные | конкретные значения, которые вводим |
| шаги | пронумерованные действия, однозначные и воспроизводимые |
| ожидаемый результат | что должно произойти — задаётся ДО выполнения |
| фактический результат | что произошло на самом деле — заполняется ПОСЛЕ |

**Признаки хорошего тест-кейса:**
- **Однозначность** — два разных человека выполнят его одинаково. Не «ввести некорректное значение», а «ввести Y = 10».
- **Атомарность** — одна проверка на кейс. Если кейс упал, сразу понятно, что именно сломалось.
- **Независимость** — не зависит от результата других кейсов и от порядка выполнения.
- **Воспроизводимость** — даёт один и тот же результат при повторном запуске.
- **Ожидаемый результат написан заранее** — иначе есть соблазн подогнать его под то, что получилось.

**Чем отличается от чек-листа и тест-сьюта.** *Чек-лист* — просто список того, что надо проверить, без шагов («проверить вход», «проверить выход»); пишется быстро, но требует опыта от исполнителя. *Тест-кейс* — подробная инструкция. *Тест-сьют* (test suite) — набор кейсов, объединённых по смыслу; у нас это два файла: `auth.spec.js` и `points.spec.js`.

### Позитивные и негативные тесты

**Позитивный** тест проверяет, что при правильных данных система работает как надо. **Негативный** — что при неправильных данных она корректно отказывает: не падает, не пропускает мусор, показывает понятное сообщение.

Негативных кейсов обычно должно быть не меньше, чем позитивных: путей «сделать неправильно» всегда больше, чем путей «сделать правильно». У нас 8 негативных и 7 позитивных.

### Техники тест-дизайна

Проверить все возможные комбинации входных данных невозможно — их бесконечно много. Техники тест-дизайна помогают выбрать минимальный набор проверок, который находит максимум ошибок.

**1. Эквивалентное разделение (equivalence partitioning).** Разбиваем все возможные значения на классы, внутри которых поведение системы одинаково, и берём по одному представителю из каждого класса. Для поля Y с допустимым диапазоном (-3; 5) классы такие:

| Класс | Пример значения | Ожидание |
|---|---|---|
| Меньше -3 | -10 | отклонить |
| Внутри диапазона | 1 | принять |
| Больше 5 | 10 | отклонить |
| Не число | «abc» | отклонить |
| Пусто | «» | отклонить |

Проверять и -10, и -20, и -100 бессмысленно: они из одного класса, система обработает их одинаково.

**2. Граничные значения (boundary value analysis).** Ошибки чаще всего живут на границах — из-за путаницы `<` и `<=`. Поэтому к каждому классу добавляют проверку его краёв. Для диапазона (-3; 5), где границы **не** включаются:

| Значение | Ожидание | Почему интересно |
|---|---|---|
| -3 | отклонить | ровно граница, не входит |
| -2.9 | принять | сразу за границей внутри |
| 4.9 | принять | сразу перед границей |
| 5 | отклонить | ровно граница, не входит |

**3. Таблица решений (decision table).** Применяется, когда результат зависит от комбинации нескольких условий. У нас результат «попала / не попала» зависит от X, Y и R одновременно, и от того, в какой четверти оказалась точка — область состоит из разных фигур в разных четвертях.

**4. Предугадывание ошибок (error guessing).** Опыт подсказывает типичные больные места: пустые поля, нули, отрицательные числа, очень длинные строки, спецсимволы, двойной клик по кнопке, кнопка «назад» в браузере.

**5. Попарное тестирование (pairwise).** Когда параметров много, проверяют не все комбинации, а все пары значений — это резко сокращает число тестов при сопоставимой находимости ошибок.

### Виды функционального тестирования по цели

- **Дымовое (smoke)** — быстрая проверка, что основное вообще работает и есть смысл тестировать дальше. У нас это, по сути, TC-001 и TC-006: если не работает регистрация и вход, дальше проверять нечего.
- **Регрессионное** — повторный прогон тестов после изменений, чтобы убедиться, что ничего не сломалось. Ровно для этого нужна автоматизация: прогнать 15 кейсов руками — полчаса, автоматически — 10 секунд.
- **Повторное (retest)** — проверка конкретного исправленного дефекта.
- **Приёмочное** — финальная проверка перед сдачей.

### Автоматизация: что важно знать

Автоматизировать имеет смысл то, что выполняется часто и даёт стабильный результат. Разовую проверку дешевле сделать руками.

Три понятия, которые обязательно спросят:

**Изоляция тестов.** Каждый тест должен работать независимо: не полагаться на данные, оставленные другим тестом, и не мешать другим. У нас это сделано генерацией уникальных логинов по метке времени (`user${Date.now()}`) и очисткой `localStorage` перед каждым тестом. Иначе второй прогон падал бы: пользователь уже создан.

**Подготовка данных через API, а не через интерфейс.** Если тесту нужен зарегистрированный пользователь, его быстрее и надёжнее создать HTTP-запросом, чем прокликивая форму регистрации. Плюс: если сломается регистрация, упадёт только тест регистрации, а не все остальные заодно.

**Нестабильные («мигающие», flaky) тесты.** Тест, который то проходит, то падает без изменений в коде, — хуже отсутствующего: ему перестают верить. Главная причина — гонки: тест проверяет результат раньше, чем страница успела его отобразить. Лечится не паузами `sleep`, а «умными ожиданиями»: Playwright сам ждёт, пока элемент появится и станет кликабельным. В конфигурации у нас стоит `retries: 1` — один повтор упавшего теста, чтобы случайная сетевая задержка при старте контейнеров не роняла весь прогон.

## Как устроены наши функциональные тесты

### Структура

```text
functional-tests/
├── Dockerfile             образ на базе mcr.microsoft.com/playwright с браузерами
├── package.json           зависимость @playwright/test строго версии 1.59.1
├── playwright.config.js   настройки: браузер, адрес приложения, отчёты, повторы
└── tests/
    ├── auth.spec.js       TC-001 ... TC-008: регистрация и вход
    └── points.spec.js     TC-009 ... TC-015: точки, доступ, выход
```

### Конфигурация

```javascript
module.exports = defineConfig({
    testDir: './tests',
    retries: 1,                                          // один повтор упавшего теста
    reporter: [['list'], ['html', {open: 'never'}]],     // построчный вывод + HTML-отчёт
    use: {
        headless: true,                                  // браузер без окна
        baseURL: process.env.BASE_URL || 'http://localhost:3000',
        screenshot: 'only-on-failure',                   // скриншот при падении
    },
    projects: [{name: 'chromium', use: {browserName: 'chromium'}}],
});
```

`baseURL` берётся из переменной окружения: при локальном запуске это `http://localhost:3000`, а внутри Docker-сети — `http://frontend:3000`, потому что браузер там работает в контейнере и обращается к сервису по имени.

### Как написан тест

```javascript
test('006: successful login redirects to /app', async ({page}) => {
    const username = `loginuser_${Date.now()}`;   // уникальный логин
    await registerApi(username, 'password');      // подготовка данных через API

    await page.getByPlaceholder('Логин').fill(username);
    await page.getByPlaceholder('Пароль').fill('password');
    await page.getByRole('button', {name: 'Войти'}).click();

    await expect(page).toHaveURL(/\/app$/);        // проверка результата
});
```

Три части любого теста: **подготовка** (создали пользователя), **действие** (заполнили форму и нажали кнопку), **проверка** (`expect` — оказались на нужной странице). Это схема **AAA**: Arrange — Act — Assert.

### Как искать элементы на странице

Порядок предпочтения — от надёжного к хрупкому:

```javascript
page.getByRole('button', {name: 'Войти'})   // по роли и видимому тексту - лучший вариант
page.getByPlaceholder('Логин')              // по подсказке в поле
page.getByText('Неверный логин или пароль') // по тексту
page.locator('#y-input')                    // по id - когда текста нет
page.locator('input[name="x"][value="1"]')  // по атрибутам - для радиокнопок
```

`getByRole` предпочтительнее CSS-селекторов: он не сломается от изменения вёрстки и заодно проверяет доступность интерфейса. Селекторы вида `div > div:nth-child(3) > span` использовать не стоит — они ломаются от любой правки разметки.

### Ожидания

Ключевое правило: **никаких `sleep`**. Playwright ждёт сам:

```javascript
await expect(page.getByText('уже существует')).toBeVisible();  // ждёт появления, до таймаута
await expect(page).toHaveURL(/\/app$/);                        // ждёт смены адреса
```

`await` перед каждым действием обязателен — иначе тест побежит дальше, не дождавшись результата, и упадёт непредсказуемо.

## Сложности при работе с функциональными тестами и их решения

Список реальных проблем, с которыми пришлось разбираться, и что помогло.

**1. Тесты падали при повторном запуске.** Первый прогон проходил, второй — нет: пользователь с тестовым логином уже существовал в базе. Решение — генерировать логин с меткой времени `user${Date.now()}`, тогда каждый прогон работает со своими данными. Альтернатива — чистить базу перед каждым прогоном, но это медленнее и мешает параллельному запуску.

**2. Тесты влияли друг на друга через localStorage.** Токен авторизации, оставшийся от предыдущего теста, ломал проверку доступа неавторизованного пользователя. Решение — очистка `localStorage` в блоке `beforeEach`, который выполняется перед каждым тестом.

**3. Тесты стартовали раньше, чем приложение было готово.** В Docker контейнер с Playwright запускался, когда backend ещё поднимал Spring и подключался к базе — тесты падали примерно в половине прогонов. Решение — healthcheck-и в compose-файле и условие `depends_on: condition: service_healthy`, плюс параметр `start_period`, дающий приложению время на старт до начала проверок.

**4. Frontend в контейнере не запускался при плохой сети.** Прогон падал с ошибкой `dependency failed to start: container frontend is unhealthy`, но не всегда. В логах контейнера нашлось: `npm warn exec The following package was not found and will be installed: serve` — веб-сервер докачивался из интернета при каждом запуске контейнера. Стоило сети моргнуть, контейнер не начинал слушать порт. Решение — установить `serve` на этапе сборки образа, а не при запуске. Вывод: если контейнер тянет что-то из сети при старте, он не воспроизводимый.

**5. Не было видно результатов тестов.** Цель отрабатывала и писала «успешно», но какие именно тесты прошли — непонятно. Причина оказалась не в Playwright: Gradle выполняет сборку в отдельном фоновом процессе-демоне, и вывод запускаемых программ уходил в его консоль, а не в консоль пользователя. Решение — читать вывод подпрограммы в скрипте и печатать построчно; заодно подключён HTML-отчёт.

**6. Тесты не работали без Docker и было непонятно почему.** Цель `func-tests-local` падала с `BUILD FAILED` — потому что тесты открывали `http://localhost:3000`, а приложение не было запущено. Решение — понятное сообщение в выводе цели о том, что приложение должно быть запущено, и раздел в README о том, как его поднять.

**7. Долгая установка выглядела как зависание.** Первый запуск локальной цели скачивал зависимости и браузер Chromium (~1 минута), и в это время Gradle показывал только полоску прогресса. Решение — выполнять установку только при первом запуске (проверка наличия `node_modules`); повторные прогоны занимают ~10 секунд.

**8. Разный адрес API снаружи и внутри Docker.** На своей машине браузер обращается к backend по `localhost:8080`, а внутри Docker-сети — по имени сервиса `backend:8080`. React подставляет такие переменные на этапе сборки, а не при запуске, поэтому адрес вынесен в build-аргумент и передаётся разными значениями из двух compose-файлов.

**9. Версия Playwright расходилась с Docker-образом.** Официальный образ жёстко привязан к версии библиотеки: браузеры внутри соответствуют конкретному релизу. Пока в зависимостях стоял диапазон `^1.44.0`, обновление могло разойтись с образом и сломать прогон. Решение — точная версия `1.59.1` в `package.json` и синхронизированный lock-файл.

**10. Занятые порты.** Приложение слушает 8080, 3000 и 5431. Если порт занят другой программой, Docker отказывается стартовать с ошибкой `address already in use`. Диагностика: `lsof -nP -iTCP:8080 -sTCP:LISTEN`, затем `kill <PID>`. Частая причина — забытые контейнеры от прошлого запуска, лечится `docker compose down`.
